## EVM Contract Architecture

### Inheritance Hierarchy

```
OpenZeppelin Contracts
├── Ownable2Step           -> CertenAnchorV3
├── Pausable               -> CertenAnchorV3
├── ReentrancyGuard        -> CertenAccountV3
└── ERC-4337 Interfaces    -> CertenAccountV3

CertenAnchorV3
  |- stores merkle roots
  |- verifies Merkle proofs
  |- emits AnchorEvent
  |- pausable by owner

BLSZKVerifier
  |- stateless Groth16 verifier
  |- generated verification key
  |- ~220K gas per verify

CertenAccountV3
  |- implements IAccount (ERC-4337)
  |- linked to ADI via anchor
  |- validates governance proofs
  |- executes intents

CertenAccountFactory
  |- CREATE2 deployment
  |- ADI-to-address mapping
  |- deterministic addresses
```

## CertenAnchorV3

The anchor contract is the on-chain root of trust for Accumulate state.

### Storage

```solidity
mapping(bytes32 => bool) public anchored;          // merkleRoot => exists
mapping(bytes32 => uint256) public anchorTimestamp;  // merkleRoot => block.timestamp
address public blsVerifier;                          // BLSZKVerifier address
```

### Key Functions

**`anchor(bytes32 merkleRoot, bytes calldata zkProof, uint256[] calldata publicInputs)`**

1. Verify the Groth16 proof via `BLSZKVerifier.verify(zkProof, publicInputs)`
2. Verify that `publicInputs[0] == uint256(merkleRoot)` (proof binds to this root)
3. Store `anchored[merkleRoot] = true` and record timestamp
4. Emit `AnchorEvent(merkleRoot, block.timestamp, msg.sender)`

**`verifyProof(bytes32 merkleRoot, bytes32[] calldata proof, bytes32 leaf)`**

1. Check `anchored[merkleRoot] == true`
2. Compute Merkle root from `leaf` and `proof` path
3. Return `computedRoot == merkleRoot`

This is a read-only function (view) used by `CertenAccountV3` and external verifiers.

### Security Features

- **Pausable**: Owner can pause anchoring in emergencies
- **Access control**: Only whitelisted validators can call `anchor()`
- **Immutable binding**: `merkleRoot` cannot be modified after storage
- **Event emission**: All anchors emit events for indexing

### `merkleRoot` Computation

The `merkleRoot` is a SHA-256 hash that binds all proof cycle outputs:

```
merkleRoot = SHA-256(
  L1.root ||
  L2.root ||
  L3.root ||
  L4.root ||
  G0.hash ||
  G1.hash ||
  G2.hash ||
  BLS.aggregateSignature
)
```

## BLSZKVerifier

A stateless contract that verifies Groth16 proofs. The verification key is embedded at deployment time (generated by gnark's trusted setup).

**Gas cost**: ~220,000 gas per verification call (constant, regardless of the number of validators who signed the BLS aggregate).

This is significantly cheaper than on-chain BLS pairing operations, which would cost millions of gas for 7 validators.

### Verification

```solidity
function verify(
    bytes calldata proof,       // Groth16 proof (A, B, C points)
    uint256[] calldata inputs   // Public inputs [merkleRoot, ...]
) external view returns (bool)
```

The proof demonstrates that a valid BLS aggregate signature exists over the given public inputs, without revealing the signature on-chain.

## CertenAccountV2 / V3

ERC-4337 smart contract accounts governed by ADI key structures.

### ERC-4337 Interface

```solidity
function validateUserOp(
    UserOperation calldata userOp,
    bytes32 userOpHash,
    uint256 missingAccountFunds
) external returns (uint256 validationData);

function execute(
    address dest,
    uint256 value,
    bytes calldata func
) external;

function executeBatch(
    address[] calldata dest,
    uint256[] calldata value,
    bytes[] calldata func
) external;
```

### Intent Execution Flow

1. Validator submits a `UserOperation` to the ERC-4337 `EntryPoint`
2. `EntryPoint` calls `validateUserOp()` on the `CertenAccountV3`
3. `CertenAccountV3`:
   a. Extracts the intent data from the UserOp calldata
   b. Queries `CertenAnchorV3.verifyProof()` to verify the Merkle proof
   c. Verifies that the governance requirements are met (proof includes valid G0-G2)
   d. Returns validation success
4. `EntryPoint` calls `execute()` on the account
5. `CertenAccountV3` executes the target call (transfer, contract interaction)

### V2 vs V3 Differences

| Feature | V2 | V3 |
|---------|----|----|
| Intent protocol | Single-leg only | Multi-leg, batch |
| Governance proof | Basic key check | Full G0-G2 chain verification |
| Batch execution | No | Yes (`executeBatch`) |
| Gas sponsorship | No | Via ERC-4337 paymaster |
| Multi-chain nonce | No | Per-chain nonce tracking |

## CertenAccountFactory

Deploys `CertenAccountV3` instances using CREATE2 for deterministic addressing.

```solidity
function createAccount(
    bytes32 adiHash,    // SHA-256(ADI URL), e.g., SHA-256("acc://org.acme")
    bytes32 salt        // Additional salt for uniqueness
) external returns (address account);

function getAddress(
    bytes32 adiHash,
    bytes32 salt
) external view returns (address);
```

### Deterministic Addressing

The account address is computed as:

```
address = CREATE2(
    factory_address,
    keccak256(adiHash || salt),
    keccak256(CertenAccountV3.initcode || adiHash)
)
```

Since the factory is deployed at the same address on all EVM chains (using CREATE2 on the factory itself), and the same `adiHash` + `salt` produce the same address, an ADI maps to the same account address across all EVM chains.

## Deployment Scripts

### `Deploy.s.sol` - Main Orchestration

Deploys all contracts in order:

1. Deploy `BLSZKVerifier` (stateless, no constructor args)
2. Deploy `CertenAnchorV3(blsVerifierAddress, owner)`
3. Deploy `CertenAccountFactory(anchorAddress, entryPointAddress)`
4. Configure: whitelist validators on anchor, verify deployment

### Per-Chain Configuration

The deploy script reads chain-specific configuration from environment variables:

```bash
# Deploy to Sepolia
CHAIN=sepolia \
DEPLOYER_KEY=0x... \
ENTRY_POINT=0x5FF137D4b0FDCD49DcA30c7CF57E578a026d2789 \
forge script script/Deploy.s.sol --rpc-url $SEPOLIA_RPC --broadcast
```

## Non-EVM Platforms

### Solana (Anchor)

```
solana/
├── programs/
│   └── certen/
│       └── src/
│           ├── lib.rs             # Program entry point
│           ├── anchor.rs          # Anchor instruction (PDA-based)
│           ├── verify.rs          # Merkle proof verification
│           └── account.rs         # ADI-linked account management
├── tests/
└── Anchor.toml
```

Key differences from EVM:
- **PDAs** (Program Derived Addresses) instead of CREATE2
- **Account model** instead of contract storage
- **Instructions** instead of function calls
- Address derived as `PDA(program_id, [b"certen", adi_hash])`

### CosmWasm

```
cosmwasm/
├── src/
│   ├── contract.rs               # instantiate, execute, query handlers
│   ├── msg.rs                    # Message type definitions
│   ├── state.rs                  # Contract state (cw-storage-plus)
│   └── error.rs                  # Custom error types
├── tests/
└── Cargo.toml
```

Three entry points:
- **`instantiate`**: Set owner, verifier config
- **`execute`**: `Anchor{}`, `ExecuteIntent{}`
- **`query`**: `VerifyProof{}`, `GetAnchor{}`

### NEAR

```
near/
├── src/
│   ├── lib.rs                    # Contract entry point
│   ├── anchor.rs                 # Anchor storage and verification
│   └── account.rs                # ADI account management
├── tests/
└── Cargo.toml
```

Uses `near-sdk` with `#[near_bindgen]` for contract methods.
