Cryptographic Pipeline

The 9-Phase Proof Cycle

End-to-end verifiable path from user intent on Accumulate through BFT consensus, on-chain anchoring, external execution, and cryptographic write-back. Every phase produces auditable artifacts. Two distinct BLS signing events occur: pre-execution (Phase 3/4, domain CERTEN_ATTESTATION_V1) where validators authorize the operation before it reaches the external chain, and post-execution (Phase 8, domain CERTEN_RESULT_ATTESTATION_V1) where validators attest to the observed result.

Accumulate Origin
1
Intent Submission (WriteData)
api-bridge web-app API Layer

User submits a CERTEN_INTENT transaction to Accumulate via the Web App and API Bridge. The intent is a canonical 4-blob structure (intentData, crossChainData, governanceData, replayData) that specifies the target chain, operation, and governance authority (ADI key book). The API Bridge constructs the transaction, sends the hash to Key Vault for Ed25519 signing, then submits the signed transaction to Accumulate. The OperationID—a SHA-256 hash of all 4 blobs—becomes the unique identifier tracked through the entire proof cycle.

Data Flow
Web App → API Bridge (:8085)
  POST /intent/create
  { adiURL, targetChain, operation, keyBook }

API Bridge → Key Vault (window.certen)
  signHash(txHash)

API Bridge → Accumulate (v3 API)
  WriteData(signedTx) → TXID
Canonical 4-Blob Intent Model
CertenIntent {
  Blob 0 intentData // operation type, ADI URL, metadata
  Blob 1 crossChainData // target chain, contract addr, calldata
  Blob 2 governanceData // key book URL, authority level, sigs
  Blob 3 replayData // nonce, expiry, dedup fields
}

OperationID = SHA-256(blob0 || blob1 || blob2 || blob3)
// Single source of truth for identity through all 9 phases
2
Lite Client Proof Generation (L1–L4)
validator Protocol

Validators construct a 4-layer cryptographic proof chain that anchors the intent data to Accumulate's genesis trust. Each layer is a SHA-256 Merkle proof verifiable independently. The LiteClientProofGenerator queries Accumulate's CometBFT RPC endpoints across multiple BVN (Block Validator Network) partitions to build real proofs.

Proof Layers
L1 Account State → BPT Root
   SHA-256 Merkle Patricia Tree proof
   Proves intent data exists in account state
   LiteClientProofData.AccountHash

L2 BPT Root → Block Hash (AppHash)
   Commitment to full blockchain state
   LiteClientProofData.BPTRoot → becomes crossChainCommitment

L3 Block Hash → Validator Signatures
   Consensus proof from Accumulate validators
   LiteClientProofData.BlockHash + ConsensusProof

L4 Validator Set → Genesis Trust
   Completes trustless verification chain
   Validator set Merkle proof to genesis anchor
Proof Artifact Output
CertenProof.LiteClientProof {
  CompleteProof *proof.CompleteProof
  AccountHash []byte // L1
  BPTRoot []byte // L2
  BlockHash []byte // L3
  ConsensusProof *proof.ConsensusProof // L3-L4
  AccountData *api.AccountInfo
}

3
Validator Block Building + Governance Proofs (G0–G2)
validator Protocol

Validators assemble a ValidatorBlock containing the operation commitment, governance proof, cross-chain proof, and lite client proof. Governance proofs verify ADI authority at three levels. Critically, each validator BLS-signs the OperationID during this phase using DomainAttestation ("CERTEN_ATTESTATION_V1"). This pre-execution BLS aggregate signature is embedded in the GovernanceProof.BLSAggregateSignature field and will be verified on-chain by the BLSZKVerifier in Phase 6.

Governance Levels
G0 Inclusion & Finality Only
   Entry hash, TXID, receipt data
   No governance verification

G1 Governance Correctness (default)
   Authority snapshot at execution time
   Key page state + Ed25519 signature verification
   Threshold satisfaction proof

G2 Governance + Outcome Binding
   Payload authenticity + effect verification
   Receipt binding + witness consistency
   Uses txhash CLI for payload verification
Pre-Execution BLS Signing (1st BLS Event)
This is the FIRST of two BLS signing events in the proof cycle.

Each validator signs:
  message = OperationID (SHA-256 of 4-blob intent)
  domain = "CERTEN_ATTESTATION_V1"
  key = validator's BLS12-381 private key

blsSig, _ := blsKeyManager.SignWithDomain(
  []byte(operationID), bls.DomainAttestation)

Result stored in:
  GovernanceProof.BLSAggregateSignature

Purpose: Proves validator set authorized this operation
before it is submitted to the external chain.

4
BFT Consensus
validator Protocol

The 7-validator CometBFT network reaches consensus on the ValidatorBlock. Requires 2/3+ validator signatures (at least 5 of 7). Validators exchange blocks via CometBFT P2P on port 26656 and commit via BFT rounds (propose → prevote → precommit → commit). The BLS aggregate signature from Phase 3 is included in the committed block—once consensus passes, the ValidatorBlock (with its embedded BLS authorization) is ready for on-chain submission.

Consensus Parameters
Validators: 7 nodes (100 voting power each)
Threshold: 2/3 × 700 = 467 minimum
Minimum: 5 validators must sign
Protocol: CometBFT P2P (:26656)
RPC: CometBFT RPC (:26657)
BFT Round Flow
1. Propose
   Leader proposes ValidatorBlock with L1-L4 + G0-G2 proofs
   Includes pre-execution BLS aggregate signature

2. Prevote
   Validators verify proof integrity, vote to accept

3. Precommit
   2/3+ prevotes received, validators lock on block

4. Commit
   Block committed, passed to TargetChainExecutor
   for on-chain anchoring (Phase 5-6)

On-Chain Anchoring (External)
5
Anchor Commitment Derivation
validator Contracts

Validators derive three 32-byte commitment hashes from the ValidatorBlock, then combine them with the ADI URL hash into an immutable 4-leaf sorted Merkle tree. This merkleRoot is the tamper-proof binding submitted to the destination chain. The governanceRoot is derived directly from the Phase 3 BLS aggregate signature: SHA-256(blsAggregateSignature), cryptographically binding the validator consensus authorization into the anchor.

Merkle Tree Structure
              merkleRoot (immutable)
             /              \
         hash01            hash23
        /     \           /     \
   adiURLHash  opCommit   crossChain  govRoot

operationCommitment — intent 4-blob hash (OperationID)
crossChainCommitment — BPT state root (from L2)
governanceRoot — SHA-256(BLS aggregate signature from Phase 3)

6
Smart Contract Execution
contracts On-Chain

Three sequential smart contract calls execute on the destination chain. Each call verifies a different aspect of the proof before allowing on-chain state changes. TX 2 is where the pre-execution BLS signatures from Phase 3/4 are verified on-chain—the BLSZKVerifier runs a Groth16 ZK-SNARK pairing check to confirm the validator set authorized this operation before execution.

Contract Calls & Verification
TX 1 CertenAnchorV4.createAnchor()
   Records bundleId, adiURLHash, commitments
   Computes immutable 4-leaf merkleRoot on-chain
   Stores Accumulate block height
   Requires onlyValidator + whenNotPaused
   ~100-150k gas

TX 2 executeComprehensiveProof()
   Verifies Merkle proof (L1-L4 sorted hash path)
   Verifies Phase 3/4 BLS via BLSZKVerifier
     _verifyBLSProof() → verifyBLSSignature()
     SECURITY: messageHash must == anchorId (anti-replay)
   Verifies governance proof (G0/G1/G2 levels)
     KeyPage Merkle proof OR GovernanceVerifier contract
   Verifies commitment binding (op, cc, gov match anchor)
   Checks anti-replay (commitment + nonce)
   Checks proof expiration timestamp
   ~300-500k gas

TX 3 executeWithGovernance()
   Requires proof already executed (TX 2 passed)
   Executes target operation via low-level call
   ~220k gas
BLS ZK-SNARK Verification Detail (Verifies Phase 3/4 Signatures)
This verifies the PRE-EXECUTION BLS signatures from Phase 3/4.
Validators signed the OperationID with DomainAttestation
BEFORE the intent reached the external chain.

BLSZKVerifier (BLSZKVerifier.sol) uses Groth16 ZK-SNARK:

Off-chain: Go prover (gnark) generates ZK proof that
  BLS12-381 aggregate signature is valid
On-chain: Verifies Groth16 proof on BN254 curve

Proof structure (BN254 curve points):
  a: uint256[2] (G1 point)
  b: uint256[2][2] (G2 point)
  c: uint256[2] (G1 point)

Public inputs verified:
  publicInputs[0] = messageHash
  publicInputs[1] = pubkeyCommitment
  publicInputs[2] = signedVotingPower
  publicInputs[3] = totalVotingPower
  Threshold: signedVotingPower ≥ totalVotingPower × 2/3

EVM pairing check (ecPairing precompile at address 8):
  e(-A, B) × e(α, β) × e(vk_x, γ) × e(C, δ) = 1

G2 point encoding: gnark [real, imaginary] →
  EVM [imaginary, real] (Fp2 element swap)

Cost: ~220k gas per verification

// Contract: BLSZKVerifier.sol
// Called by: CertenAnchorV4._verifyBLSProof()
Verification Result & Failure Reasons
VerificationResult {
  merkleVerified bool // L1-L4 proof path
  governanceVerified bool // G0/G1/G2 level
  blsVerified bool // Phase 3/4 BLS ZK-SNARK
  commitmentVerified bool // op/cc/gov match anchor
  timestampValid bool // proof not expired
  nonceValid bool // anti-replay check
}

ALL six must pass — any failure reverts with reason:
  "Merkle proof verification failed"
  "BLS signature verification failed"
  "Governance proof verification failed"
  "Commitment verification failed"
  "Proof timestamp expired"
  "Nonce already used (replay attack prevented)"

// Contract: CertenAnchorV4.sol:1048-1092
Cryptographic Loop Closure
7
External Chain Result Observation
validator Observation

The ExternalChainObserver watches the destination chain for transaction finalization. After 12+ block confirmations (configurable; 2 for testnets), it constructs Merkle inclusion proofs that cryptographically prove the transaction exists in the finalized block. The observer polls every 12 seconds (one Ethereum block time) with a 30-minute timeout. Each result is linked to previous results via a hash chain (PreviousResultHash), creating a verifiable lineage of all execution results.

ExternalChainResult Structure
ExternalChainResult {
  // Hash Chain Binding
  ResultID [32]byte // deterministic: chain+block+tx
  PreviousResultHash [32]byte // links to prior result
  AnchorProofHash [32]byte // binds to L3 anchor proof
  SequenceNumber uint64

  // Chain Identification
  Chain, ChainID, TxHash
  BlockNumber, BlockHash

  // Block State Roots
  TransactionsRoot // Merkle root of all txs in block
  ReceiptsRoot // Merkle root of all receipts
  StateRoot // State trie root

  // Merkle Inclusion Proofs
  TxInclusionProof [][]byte // RLP-encoded trie proof
  ReceiptInclusionProof [][]byte // RLP-encoded trie proof

  // Execution Outcome
  Status // 1=success, 0=revert
  Logs, GasUsed
  ConfirmationBlocks // ≥12 for finality
}

8
Multi-Validator Result Attestation
validator Protocol

Each validator independently verifies the external chain result, then signs an attestation with their BLS key. This is the SECOND BLS signing event in the proof cycle, using a different domain (CERTEN_RESULT_ATTESTATION_V1) than the Phase 3/4 pre-execution signing. The ResultVerifier creates individual attestations, and the AttestationCollector aggregates them via real BLS signature aggregation (gnark-crypto) once 2/3+ voting power threshold is met.

Post-Execution BLS Signing (2nd BLS Event)
This is the SECOND of two BLS signing events in the proof cycle.

Each validator signs:
  message = H("CERTEN_RESULT_ATTESTATION_V1"
            || resultHash || bundleID || blockNumber)
  domain = "CERTEN_RESULT_ATTESTATION_V1" (bls.DomainResult)
  key = validator's BLS12-381 private key (same key, different domain)

sig := v.blsPrivateKey.SignWithDomain(
  messageHash[:], bls.DomainResult)

Domain separation ensures Phase 3/4 signatures
CANNOT be replayed as Phase 8 attestations and vice versa.

Attestation & Aggregation
ResultAttestation (per validator) {
  ResultHash [32]byte // hash of ExternalChainResult
  BundleID [32]byte // original ValidatorBlock bundle
  ValidatorID string
  ValidatorAddress common.Address
  ValidatorIndex uint32 // index in validator set
  BLSSignature []byte // individual BLS sig
  MessageHash [32]byte // domain-separated hash signed
  BlockNumber *big.Int // external block observed
  Confirmations int // confirms at attestation time
}

AggregatedAttestation {
  AggregateSignature []byte // real BLS aggregation (gnark-crypto)
  ValidatorBitfield []byte // bitmap of which validators signed
  ValidatorRoot [32]byte // Merkle root of validator set
  SnapshotID [32]byte // validator set snapshot
  TotalVotingPower uint64
  SignedVotingPower uint64
  ThresholdMet bool
}

Threshold: 2/3+ voting power (467/700 minimum)
Verification Checks (Per Validator)
Each validator independently verifies before signing:

1. Transaction targeted expected contract address
2. Operation commitment matches original intent OperationID
3. Success/failure matches expectations
4. Event logs match expected emissions
   (AnchorCreated, ProofVerified, GovernanceExecuted)
5. Merkle inclusion proofs (tx + receipt) are valid
6. Block confirmations ≥ 12 (finality guarantee)

ExecutionCommitmentBuilder pre-computes expected
function selectors and event signatures to verify
the executor didn't substitute a different transaction.

9
Write-Back to Accumulate
validator Accumulate

The ResultWriteBack constructs a SyntheticTransaction of type CERTEN_EXECUTION_RESULT and submits it to Accumulate, closing the cryptographic loop. The complete proof chain—from intent through external execution and attestation—is recorded as an auditable artifact. The SyntheticTxBuilder packages the Phase 8 aggregated BLS attestation alongside the Phase 7 external chain proofs into a single Accumulate data entry, creating a permanent on-chain record.

SyntheticTransaction Payload
SyntheticTransaction {
  TxType: "CertenProofResult"
  Principal: "acc://certen.acme/results"

  Body: SyntheticTxBody {
    ProofCycleResult {
      OperationID [32]byte
      TargetChain string
      ExecutionTxHash string
      ExecutionBlock *big.Int
      ExecutionStatus string // "success" | "reverted"
    }

    ExternalChainProof { // from Phase 7
      ExternalStateRoot [32]byte
      ExternalTxRoot [32]byte
      ExternalReceiptRoot [32]byte
      TxInclusionProof [][]byte
      ReceiptInclusionProof [][]byte
    }

    DataEntry { // Accumulate WriteData entry
      EntryHash, AccountURL, WriteTimestamp
    }
  }

  AttestationProof: AggregatedAttestation // from Phase 8
    .AggregateSignature []byte
    .ValidatorBitfield []byte
    .ThresholdMet true

  Status: pending → submitted → confirmed
}

ProofCycleCompletion {
  Phase7: ExternalChainResult
  Phase8: AggregatedAttestation
  Phase9: SyntheticTransaction
  Success: true
}

Proof Lifecycle State Machine
pending → batched → anchored → attested → verified
                                   \→ failed (any state)

Phase 1: pending // intent submitted
Phase 2-4: batched // proof built, consensus reached
Phase 5-6: anchored // on-chain anchor confirmed
Phase 7-8: attested // 2/3+ validators attested result
Phase 9: verified // write-back confirmed on Accumulate

5 Start Firebase Emulators + Pending Service

cd ~/certen/certen-web-app cp .env.example .env # Edit .env: set VITE_API_BASE_URL=http://localhost:8085 npm install npm run dev
