# Glossary

Alphabetical reference of key terms used across the Certen Protocol documentation.

---

**ADI (Accumulate Digital Identifier)**: A human-readable, hierarchical identity on the Accumulate blockchain (e.g., `acc://organization.acme`). ADIs contain key books, token accounts, and data accounts. In the Certen Protocol, ADIs serve as the root identity that governs cross-chain accounts.

**Anchor / Anchoring**: The process of committing an Accumulate state root to a destination blockchain via a smart contract transaction. Anchoring creates a verifiable on-chain record that a particular Accumulate state existed at a given point in time.

**BLS12-381**: A pairing-friendly elliptic curve used for BLS aggregate signatures. Validators sign proof bundles with individual BLS keys, and these signatures are aggregated into a single signature that can be verified against all signers simultaneously.

**BPT (Binary Patricia Trie)**: The data structure used by Accumulate to organize account state within a partition. Phase L2 of the proof cycle proves inclusion in the BPT root.

**BFT (Byzantine Fault Tolerance)**: A consensus property guaranteeing correct operation as long as fewer than 1/3 of validators are malicious or faulty. Certen validators use CometBFT to achieve BFT consensus on proof generation.

**CometBFT**: The consensus engine (formerly Tendermint) used by Certen validators. Provides BFT consensus with instant finality through a propose-prevote-precommit-commit cycle. Validators communicate via P2P on port 26656 and expose an RPC on port 26657.

**CREATE2**: An EVM opcode that deploys contracts to deterministic addresses based on the deployer address, salt, and bytecode hash. Used by `CertenAccountFactory` to deploy ADI-linked accounts at predictable addresses across EVM chains.

**Custody Chain**: A concept in the Certen Protocol where the signing authority for a cross-chain account is maintained on Accumulate (the "custody" chain) rather than on the destination chain. This enables ADI governance to control accounts across all supported blockchains.

**DN (Directory Network)**: The top-level coordination layer of the Accumulate blockchain. The DN anchors partition state, providing a single root hash that represents the entire Accumulate network state. Phase L4 of the proof cycle proves inclusion in the DN anchor.

**ERC-4337**: The Ethereum account abstraction standard. Certen uses ERC-4337 to create smart contract accounts on EVM chains that are governed by ADI key structures rather than individual EOA private keys.

**gnark**: A Go library for zero-knowledge proof systems. Certen validators use gnark to generate Groth16 ZK-SNARK proofs that verify BLS aggregate signatures, enabling efficient on-chain verification (~220K gas).

**Groth16**: A zero-knowledge proof system that produces constant-size proofs with fast verification. Used by Certen to prove that a BLS aggregate signature over a proof bundle is valid, without requiring on-chain BLS pairing operations.

**Intent**: A structured data object representing a cross-chain action that an ADI wants to perform. Intents contain 4 blobs: metadata (action type, target chain), cross-chain parameters (destination address, value, calldata), governance (required signatures, thresholds), and replay protection (nonce, expiry).

**Key Book**: A container within an ADI that holds one or more key pages. Key books define the authority structure for the ADI. An ADI can have multiple key books for different levels of administrative control.

**Key Page**: A set of public keys within a key book, with an associated signature threshold (e.g., 2-of-3). Key pages can also contain delegation entries pointing to other ADIs' key books, enabling hierarchical governance.

**Kermit**: The Certen/Accumulate shared testnet environment. Validators, API Bridge, and other services run on Kermit for integration testing. Connects to Ethereum Sepolia for EVM anchoring.

**LXR**: A memory-hard proof-of-work algorithm from the Accumulate project. Used by Certen miners to audit validator proofs. LXR requires a large lookup table (up to 1GB) in memory, making it ASIC-resistant.

**Merkle Proof**: A cryptographic proof that a specific piece of data is included in a Merkle tree. Certen uses Merkle proofs at multiple levels: account state within a partition, partition state within the DN, and governance state within key structures.

**Multi-sig (Multi-Signature)**: A governance model where multiple signatures are required to authorize a transaction. Certen supports multi-sig through ADI key pages with configurable thresholds (e.g., 2-of-3 signers must approve).

**Proof Bundle**: The complete set of cryptographic proofs generated by validators in a single proof cycle. Contains Merkle proofs (L1-L4), governance proofs (G0-G2), BLS aggregate signature, and the on-chain anchor transaction hash.

**Proof Cycle**: The 9-phase process by which validators generate and anchor cryptographic proofs. Phases: L1 (Account Merkle), L2 (BPT), L3 (Root Anchor), L4 (DN Anchor), G0 (Key Page), G1 (Key Book), G2 (Authority), BLS (Aggregation), Anchor (On-chain).

**Replay Protection**: Mechanisms that prevent a signed transaction or intent from being executed more than once. Certen intents include nonces and expiry timestamps. Smart contracts track executed intents to prevent replay.

**Two-Phase Signing**: The protocol by which transactions are signed using the Key Vault extension. Phase 1 (Prepare): API Bridge constructs the transaction and returns a hash. Phase 2 (Sign + Submit): Key Vault signs the hash, and API Bridge submits the transaction with the external signature. This ensures private keys never leave the browser extension.

**ZK-SNARK (Zero-Knowledge Succinct Non-interactive Argument of Knowledge)**: A cryptographic proof system that allows one party to prove a statement is true without revealing the underlying data. Certen uses Groth16 ZK-SNARKs to prove BLS signature validity on-chain efficiently.
